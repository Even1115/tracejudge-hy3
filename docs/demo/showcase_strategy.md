# TraceJudge-Hy3 成果展示方案

适用：犀牛鸟实战任务 2「可验证场景：过程评估与错误定位」。依据 2026-09-06 当前工作区 README、阶段三／四报告及四数据集阶段报告制定；这是展示设计方案，未新增实验。

## 1. 让评审记住的一个主张

**TraceJudge-Hy3 将需求、解题说明、代码与执行证据关联起来，定位可观察的过程错误，并用分级错误证书说明判断有哪些证据、哪些可以重放验证。**

建议首页副标题：

> 基于 Hy3 的代码生成过程评估工作台。检查代码与解题说明是否一致，定位首个可观察的错误步骤，并为有执行证据支持的失败提供可重放证书。

在项目名旁补充「犀牛鸟活动个人作品」。任务要求明确标注个人／活动作品；项目身份和模型提供方应清楚区分。

项目名和一句话简介之后，第一展示区直接放演示视频／成果预览。视频是最终核心交付物，应让评审先看到完整流程和系统实际呈现的成果，再深入案例、设计与实验依据。

视频之后用公开 `reasoning_swap` 解释项目价值：代码计算平均值、测试通过，解题说明却声称取最大值。让读者通过一个具体问题理解系统的处理方法。这里评估的是模型输出的说明与实现计划，不能描述为读到了模型内部思维或证明了模型真实理解。

## 2. 按贡献组织设计思路

| 展示主题 | 为什么这样设计 | 实际实现与证据 | 适合采用的表述 |
| --- | --- | --- | --- |
| 四层对齐 | 最终测试无法检查说明与实现之间的矛盾 | 需求条款、步骤 ID、AST、执行结果和 Judge 判断关联；公开 reasoning_swap 中 Test-only 0/3、四种 Judge 均 3/3 | 将功能验证扩展到可观察的过程一致性审查 |
| 分级错误证书 | 一句“模型认为有错”缺少可复查依据 | 绑定需求、错误位置、反例与证据；按证据强度分级，confirmed 示例有独立重放记录 | 将错误判断组织成可核验的证据链 |
| 配对反事实与五方法比较 | 需要检验评估器能发现什么，也会误报什么 | 同一 57 条轨迹 × 5 方法；控制修改说明、边界等因素；保留失败与固定分母 | 用配对实验检验过程评估的收益与取舍 |
| 可靠性与成本记录 | 评估器是否稳定、是否值得使用，也需要证据 | 独立复标、重复 Judge、失败留痕；新 Demo 的 Solver／Judge 分项用量 | 同时报告效果、可信度和运行开销 |

四层结构、证据融合和证书流程可作为项目方法贡献；Docker、严格 Schema、哈希、日志和成本采集属于工程质量与实验质量。是否具有学术首创性，需要另做相关工作比较，不能由这些实现直接推出。

两项设计取舍值得主动讲：静态规则有可检查性，也可能误伤等价实现；更丰富的证据输入增加成本，但本次实验中 Full 并非所有指标最优。由此解释后续为什么要改进证据适用条件与误报校准。

## 3. 把成果分成两条证据线

### 过程评估证据：说明自己的方法表现

主要入口：[阶段三／四结果总览](../releases/phase4/phase4_contest_results_overview_v1.md)、[正式研究报告](../releases/phase4/phase3_research_report_public_v1.md)。

| 方法 | 错误检测准确率，全 57 条 | 首错步骤准确率 | 正确负类上的误报率 |
| --- | --- | --- | --- |
| Test-only | 54/57，94.7% | 0/11，0.0% | 0/43，0.00% |
| Direct LLM Judge | 55/57，96.5% | 9/11，81.8% | 1/42，2.38% |
| Four-layer Structured | 56/57，98.2% | 8/11，72.7% | 1/43，2.33% |
| Four-layer + AST | 54/57，94.7% | 10/11，90.9% | 2/42，4.76% |
| Full TraceJudge | 55/57，96.5% | 9/11，81.8% | 1/43，2.33% |

检测使用全分母并将 Provider 失败计为错误；误报率来自有效二元判断，分母不同。该研究为 42 条自然轨迹与 15 条反事实的探索性结果，283/285 个配对判断有效。不能把不同方法的最佳值拼成 Full 的成绩，也不能宣称 Full 显著优于所有基线。

辅助证据放在可展开的「可信度」区域：20/57 子集独立复标，has_error 20/20 一致、完整七字段 19/20；四个公开案例各重复 Judge 5 次，原始首错步骤成对一致率 90%。一致性与正确率分别说明；事后规范化与人工裁决不覆盖原始统计。

### 外部任务证据：说明生成与外部代码判断的覆盖和边界

入口：[四数据集阶段报告](../four_dataset_evaluation_report.md)。截至本次检查，该报告及证据包在本地工作区中，尚未进入 Git 版本记录，最终对外展示前需确认版本与公开可访问性。

| 实验 | 目前可展示结果 | 同屏说明 |
| --- | --- | --- |
| HumanEval+ | Base+Extra 157/164，95.73% | 全部 164 题有效执行；增强测试比 Base 多发现 6 个失败候选 |
| MBPP+ | Base+Extra 95/120，79.17% | 固定 120/378 子集；增强测试比 Base 多发现 22 个失败候选 |
| LiveCodeBench | 固定分母 53/60，88.33% | 58 题有效执行，2 题 Provider 失败，阶段报告尚未完整；不能用 53/58 替换主指标 |
| CodeJudge v3-A | Balanced accuracy 90.00% | 平衡 120 候选；错误检出 59/60，正确程序误报 11/60，18.33% |

前三项衡量生成代码的功能正确性；第四项衡量数据集提供代码的 judge-only 判断。它们不是四层过程评估器在四个基准上的统一分数，不能计算一个跨任务平均准确率，也不能直接验证首错定位或证书有效性。

更适合讲的两项发现：

- **增强测试揭示遗漏的功能错误。** HumanEval+ 的 Base 163/164 降至 Base+Extra 157/164；MBPP+ 的 117/120 降至 95/120。用两组带分母的对照柱展示，解释为什么仅看较弱测试不够。
- **错误检测和细粒度归因存在不同难点。** CodeJudge v3-A 的高检出伴随 18.33% 误报；v3-B 相同 50 候选的三种标签粒度，原生 exact-match 为 96%、84%、72%，但标签空间不同，不能解释为同一指标上的等比例能力下降。

难度页优先展示 LCB 的 Easy／Medium／Hard 固定选题与有效执行分母；Hard 中同时呈现错误答案、编译错误、超时及两题服务失败。CodeJudge 的 easy/middle/hard 是标签粒度，不与题目难度放在同一横轴。

## 4. README 的建议阅读顺序

首页提供三种阅读深度：约 30 秒理解价值，约 3 分钟了解设计与主要证据，需要复核时进入完整文档。所有成果有入口，不要求评审一次看完每个文件。

1. **项目定位与身份**：一句话主张、个人／活动作品标识。首屏保留「看演示／启动工作台／研究结果／复现指南」四个主入口。
2. **演示视频／成果预览**：作为简介后的第一展示区，提供可点击封面、时长和一句话流程说明，让评审直接观看“启动检查 → 真实 Hy3 运行模式 → 过程评估 → 实验结果”。当前入口为 [86 秒新版工作台录屏](assets/tracejudge_hy3_contest_demo.mp4)，模型参与、公开 Fixture、历史案例与聚合实验以画面标识区分。
3. **一个代表案例**：代码与说明并排、测试结论、过程判定，解释视频中展示能力的价值；公开构造案例标签直接放在图旁。
4. **三个核心设计**：四层对齐、分级证书、配对验证。每项用“问题 → 设计选择 → 证据 → 取舍”解释；仅保留一张架构图。
5. **成果与发现**：过程评估五方法表、外部数据集覆盖表分别展示。每表最多突出两项结论，并保留方法名、分母和状态。
6. **可信度与成本**：摘要展示人工复标、独立重放和成本追踪；稳定性细表与区间放入折叠区域或报告链接。
7. **快速体验**：Windows／macOS／Linux 各给一个入口，解释真实 Hy3 与离线 Fixture。长实验命令另放运行指南。
8. **成果导航**：按评审问题列出证据入口，再链接开发文档、配置、数据来源和版本历史。

应优先统一的现有口径：

- README 仍把完整 HumanEval+、MBPP+、Web 前端放在「v0.1 尚未实现」或后续路线中。明确区分历史 Release 范围与当前工作版成果，避免把已完成内容继续呈现为当前缺项。
- `IMPLEMENTATION_STATUS.md` 与当前首页使用同一份现状摘要；冻结的历史报告保留原文、时间和版本身份，不为展示效果改写。
- 同步「原八幕＋可选第 9 幕成本」的说明；新四数据集结果目前还未接入工作台的实验总览，不能让评审以为页面已经自动展示了最新报告。
- 将 Gate 编号、完整 SHA256、裁决细节和全部 CLI 命令移到对应证据／开发文档；首页保留可点击的验证入口。

## 5. 网页分别承担什么展示任务

| 展示区域 | 评审在这里回答的问题 | 当前基础与建议 |
| --- | --- | --- |
| 项目概览 | 为什么值得看？有哪些贡献？ | 建议新增简洁概览，简介之后先放演示视频，再放代表案例、核心设计与成果地图；与日常运行面板区分 |
| 单次过程评估 | 系统实际上怎样工作？ | 复用现有题目、解答、测试、对齐、定位、证书及请求明细 |
| 实验结果 | 效果如何？失败在哪里？ | 已有历史五方法与成本；建议补入四数据集阶段结果、难度与错误类型分布，并保持任务口径分开 |
| 证据与复现 | 这些结论能查到什么依据？ | 组织报告、配置、公开产物校验、重放记录和导出入口；标明完整重现与公开摘要核验的区别 |

错误类型分布应展示实际计数与分类来源，不用“错误类型判定准确率”代替分布图；如果相应公开汇总尚未生成，应先从允许使用的记录形成去标识化聚合。混淆矩阵 FPR 与人工复核已标错样本中的误报比例采用不同分母，应分别命名。

## 6. 两分钟视频：讲清一次闭环

新版视频时长 86.313 秒，已经占据 README 简介后的第一展示区；完整成果仍由 README 和结果页承接。视频里的运行状态、Fixture、历史案例及聚合结果必须保留各自来源标识。

| 时间 | 画面 | 要让评审理解的内容 |
| --- | --- | --- |
| 0–12 秒 | 公开 reasoning_swap 的代码／说明对照，保留案例来源标签 | 测试通过还不能验证说明与实现是否一致 |
| 12–30 秒 | 在工作台提交明确需求，开始一次 Hy3 解题；展示生成代码和步骤 | 模型在系统中承担什么工作，评估对象是什么 |
| 30–55 秒 | 执行结果与四层证据对齐 | 功能结论来自执行，过程判断有可检查的关联 |
| 55–85 秒 | 本次结论、定位与证书；有 confirmed 证书时展示重放 | 判断如何落到具体步骤，哪些错误得到执行支持 |
| 85–105 秒 | 五方法表＋外部数据集覆盖摘要 | 已做哪些实验；一项有效发现和一项需要改进的问题 |
| 105–118 秒 | 当前样本 Solver／Judge 成本、导出结果与仓库入口 | 评估开销可查，结果有可追溯产物 |

实际模型等待可以剪辑并标注“等待已压缩”。若本次 Hy3 解答正确，保留真实结论；55–85 秒中可以明确切换到另一条公开失败 Fixture，保留新的来源和 Run ID 来解释证书。不要为了展示错误而反复生成后只挑有利结果、不说明案例选择。

`reasoning_swap` 的代码本身正确，不能承诺能对它找到功能失败反例。演示它的说明失配，与演示 `boundary_deletion` 的可执行失败证书，是两种证据。

## 8. 实施优先级

1. 统一 README、实现状态与最新报告的时间线，补上个人／活动作品标识。
2. 将 README 改成上述八段主线，把已有深层材料挂到成果导航；优先把演示视频／成果预览放在简介后的第一展示区，代表案例紧随其后。
3. 为四数据集报告建立结果页入口；把尚未完成的 LCB 两题、已发布历史实验和本地待发布材料分别标注。
4. 录制一次实际 Hy3 完整流程，按证据来源剪辑成 118 秒；结果与成本导出留存，并更新首页原有视频位置的封面、主链接与状态说明。
5. 最终提交前确认 README 中的报告、视频与图片已经随目标版本公开可访问。仅本地存在的文件不等于评审已经能看到；公开摘要和来源哈希也不等于完整独立复现。
