## 案例一：max_product（item-e5b9ff02f8bd9e3f3b61）

### 公开需求 → 解答主张 → 代码行为

- 公开需求 [公开材料]：求“数组中递增子序列（increasing subsequence）元素乘积的最大值”，示例 `max_product([3, 100, 4, 5, 150, 6]) == 3000`。文本未限定子序列必须连续，也未限定元素为正数。
- 解答主张 [公开材料]：需求理解将“递增子序列”收紧为“严格递增的**连续**子数组”，依据是示例 3000 = 4×5×150 只在连续解释下成立；该收紧本身与示例一致。设计为一次扫描：递增时累乘，否则重置当前乘积。
- 代码行为 [公开材料/静态推演]：`curr_prod` 仅在 `arr[i] <= arr[i-1]` 时重置；在持续递增的段内始终累乘，从不考虑“从新元素重新开始”。

### 可独立检查的错误依据

零值反例 `[0, 2, 3]` [静态推演]：

- 输入域合法性 [公开材料]：公开需求只说“numbers”，未排除 0 或负数；该反例落在公开需求允许的输入范围内。
- 预期行为依据 [公开材料]：无论按“递增子序列”还是按解答自己的“连续递增子数组”解释，`[2, 3]` 都是合法的递增子结构，乘积 6；含 0 的子结构乘积均为 0。两种解释下的正确答案都是 6。
- 代码实算 [静态推演]：初始化 `max_prod = curr_prod = 0`；`2 > 0` → `curr_prod = 0×2 = 0`；`3 > 2` → `curr_prod = 0×3 = 0`；返回 0。与预期 6 不符。

官方证据 [官方汇总]：base 通过、plus 未通过。plus 的具体用例不可见；plus 包含类似零值边界是**与证据一致的假设**，不是已观察事实。

### 各条件判断与规则贡献（历史运行）

- `direct_judge`、`structured_judge`：均判 reasoning/aligned 正确（fn，漏判）[历史实测]。
- `full_system`：`reasoning_correct=False`，层级 reasoning，类型 P01_ALGORITHM_ERROR（次级 C01），定位引用 `design_summary` 原文（“Scan the array once from left to right…”）[历史实测]。解释中的关键推理（递增段内遇零应重启）与上面的静态推演一致；定位 quote 逐字存在于冻结字段 [公开材料]——引用存在只证明位置绑定，不单独证明错误判断正确，此处判断另有零值推演支持。
- 规则贡献：对全部 12 条冻结候选离线运行确定性规则（纯 AST），**0 条触发**；`combine_assessment` 在规则为空时完整回退到 Judge 输出。因此两个成功案例中**未观察到规则合并贡献**——`full_system` 的差异来自 Judge 看到了静态证据与官方汇总功能结果，具体由本轮 2×2 消融区分。

## 案例二：division_elements（item-caf2c4228350e46f5b68）

### 公开需求 → 解答主张 → 代码行为

- 公开需求 [公开材料]：对两个元组“逐元素执行数学除法运算（mathematical division operation element-wise）”，示例 `(10,4,6,9)/(5,2,3,3) == (2,2,2,3)`，全部为整除。
- 解答主张 [公开材料]：需求理解称“执行数学除法运算（逐元素除法）”；设计选用整数除法 `//`。解答在 `edge_cases_considered[2]` 中**自己承认**：“若要求精确数学除法可能需返回浮点数……故采用整数除法”——即该假设是解答自觉做出的取舍。
- 代码行为 [公开材料]：`tuple(a // b for a, b in zip(t1, t2))`，与步骤 S3 完全一致。

### 可独立检查的错误依据

- 整数除法假设与公开需求的关系 [公开材料]：公开文本写的是“mathematical division”，未限定整数除法或整除输入；`//` 的地板除语义（`7 // 2 == 3` 而数学除法为 3.5）与“数学除法”的字面含义存在张力。解答选择了 `//`，其依据（示例全为整除）是对示例的推断，不是需求条款。
- 预期行为的确定性 [推断]：公开需求存在真实歧义——“数学除法 + 整数示例”既可读作真除法也可读作整除场景下的简写。公开材料**无法独立确定**非整除输入下的期望输出类型（float 还是 floor）。本轮不据隐藏测试下结论。
- 官方证据 [官方汇总]：base 通过、plus 未通过。**不能**把“plus 测试包含非整除输入”写成已观察到的事实；plus 失败也可能由其他差异引起。汇总失败与“`//` 假设错误”一致，但不构成唯一解释。

### 各条件判断与规则贡献（历史运行）

- `direct_judge`、`structured_judge`：均判正确（fn）[历史实测]。
- `full_system`：`reasoning_correct=False`，层级 reasoning，类型 R03_UNSUPPORTED_ASSUMPTION（次级 P01），定位引用 `edge_cases_considered[2]` 原文 [历史实测]。判断核心——“该假设无需求条款支持”——有公开材料直接支持；其解释中“plus fail 表明更严格测试（可能含非整除情形）”一句属于推断，阅读时应按推断对待。
- 规则贡献：同案例一，本轮未触发任何规则，未观察到规则合并贡献。

## 标签争议裁决记录：division_elements（2026-09-09）

**裁决协议**：应任务要求重新审查公开需求。裁决依据仅限于：①公开需求文本与示例（可逐字核对）；②标注体系对 R03 的定义；③当前冻结标签及其 rationale（被裁决对象本身）。裁决过程中**不查阅任何方法的预测/判断输出**，不查阅隐藏测试与官方参考实现（它们不属于解答者可见的公开需求，且本裁决的标的正是”公开需求支持什么”）。如实披露：裁决者在本会话早前接触过该样本的各条件判断结果摘要，无法做到绝对盲审；因此下文给出完整的、可独立复核的文本推理链，裁决成立与否可由任何读者仅凭公开材料复验。

**裁决问题**：公开需求 “performs mathematical division operation element-wise”（示例 `(10,4,6,9)/(5,2,3,3) == (2,2,2,3)`，全部整除）下，解答选择地板除 `//` 是否构成 R03_UNSUPPORTED_ASSUMPTION（”引入公开需求不存在的假设”）？

**推理链**（全部 [公开材料] 级别）：

1. “mathematical division” 在通常数学语义中指精确除法：7/2 = 3.5。地板除 `//`（7//2 = 3）是另一种运算，需要”整数除法/地板除”的另行声明；需求文本中没有 “integer”、”floor” 或”整除”字样。
2. 唯一示例的全部整除取值 (2,2,2,3) 与 `/`、`//` 乃至四舍五入均一致，示例无法区分这些读法——示例的不确定性是真实的，但它只是”未能确证”，不是”支持地板除”。
3. 因此文本存在一个主读法（精确数学除法），示例既不能确认也不能推翻它。选择 `//` 对所有非整除输入承诺了一种需求从未陈述的语义；其依据（”示例全为整除”）是对示例的推断，不是需求条款。
4. 对照 R03 定义：被引入的假设——“输入恒整除，或地板结果可接受”——在公开需求中不存在，定义逐字满足。
5. 解答在 `edge_cases_considered` 中自述该取舍（”若要求精确数学除法可能需返回浮点数……故采用整数除法”），说明该选择是自觉的；但自觉记录影响的是可检测性，不是依据性——被文档化的无依据假设仍是无依据假设。
6. 对”歧义读法”的公正考量：即便把”整数元组示例”读作暗示整数进出约定，`//` 也只是多种整数约定之一（地板除与向零截断对负数不同，还有四舍五入），需求同样未指定是哪一种。歧义至多削弱”正确答案是什么”的确定性，**不能**把 `//` 变成有需求支持的方案。

**裁决**：维持冻结标签不变——`reasoning_correct=False`、`plan_code_aligned=True`、`process_correct=False`、`error_type=R03_UNSUPPORTED_ASSUMPTION`、首错层级 reasoning、首错步骤 null。不产生新标签版本，无需重计分；`process_pilot_v1.json` 与全部既有计分结果保持有效。原”待审核”状态关闭。

**边界**：本裁决只解决”公开需求是否支持 // 假设”，不声称非整除输入下的确切期望输出（那需要需求澄清或官方材料）；不依据官方 plus 失败反推需求语义；如未来官方材料证明数据集本意即地板除，应以新证据重开裁决，而不是回溯修改本记录。
